# BUG-7675 — Vim j/k loses the caret column

**Status: ABANDONED** · Single phase · Roadmap: `docs/roadmap.md`
Branch at build time: `bugfix/bug-7675-vim-sticky-column`.

> **Abandoned — not reproducible.** The behaviour this item was raised against is correct as it
> stands, and no fix was made. What the investigation established, over the real
> `AvaloniaEditVimBuffer` on a headless `TextEditor`:
>
> - A `j`/`k` run through a short line **does** return to the column it started in. So do
>   `<Down>`/`<Up>`, a count (`2j`), an empty intermediate line, and holding `j` against the last
>   line and coming back up. `$` still parks the run on the ends of the lines.
> - **Suspect 1 (offset round-tripping) is disproven.** Writing `CaretOffset = 20` reads back `20`,
>   and `40` reads back `40`, with word wrap both on and off. AvaloniaEdit's `Caret.Offset` getter is
>   `document.GetOffset(_position.Location)` over a setter that assigns
>   `new TextViewPosition(document.GetLocation(value))` — an exact inverse. `ValidatePosition` only
>   clamps offsets *outside* the document, which the engine never writes, because `SetCaret` clamps
>   to the line first.
> - **Suspect 2 (`ScrollToCaret`) is disproven.** `Caret.BringCaretToView` computes a rectangle and
>   calls `TextView.MakeVisible`; it never assigns `Position`, so it cannot move the caret.
> - Structurally, the symptom needs `_desiredColumn` *reset* between two `j` presses. It is private
>   to `VimEngine`, and the only route in from outside is `Reset()` — reachable from
>   `VimEditorBehavior.Refresh()`, which returns early unless the enabled flag actually flips, and
>   from `OnDocumentChanged()`, which fires on a document swap. Neither runs on a keystroke.
>
> **Not covered by the evidence:** real word wrapping. On the headless platform
> `TextArea.TextView.Bounds.Width` is `0` and a 60-character line reports a single visual row even in
> a 70px window, so "wrap on" was exercised only as a property on the control, never as a line that
> actually wrapped. Confirming that case needs a manual pass in the running app.
>
> **Noticed in passing, not this bug and not fixed:** `_desiredColumn` survives a caret move the
> engine never sees. Press `j` from column 20, then click at column 3, and the next `j` still aims
> for column 20 rather than 3. That is the opposite symptom to the one reported — the column sticking
> when vim would drop it — and it would want its own work item.

## Symptom

Moving down and up with `j` / `k` does not keep the column. From column 20 of a long line, `j` onto a short line correctly clamps the caret to that line's last character — but pressing `j` again onto another long line leaves the caret at the short line's column instead of returning to column 20.

Expected (vim's own behaviour): a vertical run remembers the column it started in, and a line too short for it only borrows the caret in passing.

## What is already known

- **The engine is not the bug.** `VimEngine` implements the sticky column: `_desiredColumn` is captured in `MoveToLine` when it is `NoDesiredColumn`, `VimMotion.Up` / `VimMotion.Down` `return` early so the reset at the end of `ApplyMotion` never runs, and `$` deliberately parks it at `int.MaxValue`.
- **It is covered by a passing test.** `VimMotionTests.AVerticalRun_RemembersTheColumnItStartedIn` asserts exactly this run (`"ab|cd\nx\nefgh"` + `jj` → `"abcd\nx\nef|gh"`) over `FakeVimBuffer`.

So the divergence is in the Desktop layer — between `VimEngine` and the real AvaloniaEdit control — and the fix belongs wherever the reproduction lands, not in the engine's motion code.

## Investigation plan

Reproduce first, at the Desktop level, over a real `TextEditor`. The two suspects, in order:

1. **`AvaloniaEditVimBuffer.CaretOffset` round-tripping.** The setter writes `TextEditor.CaretOffset`, which sets AvaloniaEdit's `Caret.Offset`; the caret re-derives its position through a visual column, so with word wrap on the offset read back is not necessarily the one written. `MoveToLine` captures the desired column as `_buffer.CaretOffset - CurrentLine.Offset` — if the read-back offset differs from the written one, every capture reads a column the engine never set.
2. **`ScrollToCaret()` → `Caret.BringCaretToView()`**, called at the end of every `Execute`, and any caret side effect it triggers.

Also confirm nothing on the Desktop side calls `VimEngine.Reset()` on caret movement — `EditorPaneView.OnCaretPositionChanged` only records line/column/offset onto the tab's ViewModel today, and `VimEditorBehavior.OnDocumentChanged` should fire on document swap only.

## Design

Fix at the layer the reproduction implicates. If it is the offset round-trip, the buffer takes responsibility for reporting the offset it was given rather than the one the control re-derived. The engine's motion code and the existing `Core` tests stay as they are.

## Acceptance criteria

- With `WordWrap` **off**: a `j` / `k` run through a short line and out the other side returns to the column it started in.
- With `WordWrap` **on**: same result — the behaviour must not depend on the wrap setting.
- Holding `j` against the last line and coming back up returns to the starting column (the case `VimMotionTests` already covers over the fake buffer, now proven over the real control).
- `$` still parks the run on the ends of lines rather than on a column.
- A regression test in `Desktop.UnitTests` drives the real `AvaloniaEditVimBuffer` over a headless `TextEditor` for the long → short → long run, with wrap on and off.
- The existing `Core.UnitTests` vim suite still passes untouched.
- Build clean with zero warnings.

## Dependencies

None.

## Out of scope

`gj` / `gk` display-line motions (moving by visual row rather than by document line when word wrap is on) — a separate feature, worth its own item if wanted · any other vim motion or operator.
